# حلقتي v2.40.8 — إصلاح تنسيق PDF والحفظ المتجهي المباشر

## سبب المشكلة في v2.40.7
مسار «حفظ PDF» أعاد رسم عناصر DOM يدويًا داخل jsPDF. كان يضع كل `.pro-report-page` داخل صفحة A4 واحدة ثم يصغّرها لتناسب الارتفاع، لذلك قسم الحفظ العام الذي يحتوي عشرات الطلاب انضغط داخل صفحة واحدة. كما أن رسم النص العربي كلمةً كلمة لم يطابق تشكيل وربط Chromium، فظهر الخط العربي مختلفًا عن المعاينة.

## الإصلاح
- «حفظ PDF» على Android يستخدم الآن **Chromium/WebView PrintDocumentAdapter نفسه** الذي يعطي المعاينة الصحيحة، لكن يكتب الناتج مباشرة إلى ملف مؤقت داخل التطبيق بدون فتح PrintManager وبدون Print Spooler.
- بعد اكتمال الكتابة والتحقق من `%PDF` والحجم، يُنسخ الملف إلى `Downloads/Halaqati` ثم يُعاد قراءته للتحقق من أنه ليس 0 بايت.
- تقسيم الصفحات، تكرار رؤوس الجداول، RTL، Cairo، ألوان العناوين، حجم الخط، نوع الخط واتجاه A4 أصبحت من محرك Chromium نفسه بدل إعادة رسمها يدويًا.
- بقي زر «طباعة» منفصلًا ويستخدم واجهة Android للطابعات الفعلية.
- يوجد fallback عالي الجودة 300 DPI + طبقة نص قابلة للبحث إذا تعذر مسار Chromium المباشر على جهاز غير متوافق.
- رسائل «جاري الحفظ / تم الحفظ / خطأ» أصبحت داخل نافذة المعاينة نفسها، فلا تختفي خلف `<dialog>`، وزر «حفظ PDF» نفسه يتحول إلى «جاري الحفظ…» ثم «تم الحفظ ✓» عند النجاح.

## لا توجد Migration
هذا تحديث للواجهة ومحرك PDF فقط؛ لا يحتاج SQL أو تغيير قاعدة البيانات.
