# مراجعة الأداء: 31 معياراً (حلقاتي ويب)

بُنيت المراجعة على الخريطة المعرفية (`.ua/`) وقياسات حقيقية في Chromium: شبكة 3G سريعة (1.6 Mbps، 150ms) و3G بطيئة (400 kbps، 400ms)، ومعالج أبطأ 4×، وخادم يحاكي GitHub Pages (gzip، `max-age=600`). الأوامر: `npm run check:perf` (قياس الإقلاع) و`npm run check:perf-boot` (ترتيب وتوازي السكربتات) و`npm run check:guardian-load`.

## التحسين المنفَّذ وقياسه
**الإقلاع كان يحمّل 65 سكربتاً كلاسيكياً واحداً بعد الآخر** (كل ملف يبدأ جلبه بعد انتهاء السابق)، فيتضاعف زمن التأخّر 65 مرة. الآن تُجلب كلها معاً (`<link rel="preload">`) ويبقى **تنفيذها متسلسلاً بالترتيب نفسه حرفياً** (تتشارك متغيرات عامة). التغيير في `src/main.js`: سلسلة `await loadClassicScript(...)` صارت قائمة بيانات `BOOT_SCRIPTS` وحلقة واحدة.

| الزيارة الأولى (4× أبطأ معالج) | قبل | بعد | الفرق |
|---|---|---|---|
| جاهزية التفاعل، 3G سريعة | 14.9 ث | **5.7 ث** | −62% |
| جاهزية التفاعل، 3G بطيئة | 44.3 ث | **21.6 ث** | −51% |
| أول رسم FCP / LCP | 1.3–1.4 / 1.5–1.6 ث | بلا تغيير (لم يكن المسار الحرج) | — |
| الزيارة المتكررة (كاش الخدمة) | ~2.6 ث (وقت الشاشة الافتتاحية) | بلا تغيير | — |

الاختبار `perf-boot-check`: الترتيب مطابق للمسجّل (65/65)، وذروة الطلبات المتزامنة 57 بعد أن كانت 1–2. ملاحظة: خادم القياس HTTP/1.1 (6 اتصالات)؛ GitHub Pages يقدّم HTTP/2 فالتحسن الفعلي أكبر غالباً. الباقي على 3G البطيئة محكوم بعرض النطاق (~950KB).

## ما لم يُنفَّذ عمداً وأسبابه
- **الشاشة الافتتاحية (~2.6ث ثابتة):** قرار تصميم، تغطي التحميل ولا تغيّر جاهزية التفاعل؛ تقصيرها يغيّر الهوية فلم أمسّها.
- **Amiri woff2، `loading=lazy`، `select` الأعمدة، حذف اعتماديات، فهارس DB:** مخاطرتها أعلى من مكسبها الآن أو تحتاج إذناً.
- **حدود القياس:** Chromium مع محاكاة شبكة ومعالج، لا جهاز فعلي؛ وHTTP/1.1 في خادم القياس.
